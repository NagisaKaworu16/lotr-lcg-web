# 已确认的项目决定

## D001 · 独立项目

魔戒 LCG 与用户的移动应用、开发者账户及消耗工作分开组织，避免串入无关记忆。

## D002 · 按阶段制作和验收

优先自动计算和规则校验，玩家保留战术选择。每次开放新阶段，验证后停在该阶段末。当前到第六阶段，不把旧手动辅助流程当作后续自动规则。

## D003 · 原版基础规则口径

以原版基础规则及官方 FAQ 1.9 为核心，依据卡牌原文显式实现，不从中文摘要自动推断能力。不含新版战役／噩梦模式。旅行窗口在旅行框架步骤之后；当前对旅行费用翻牌的厄运、涌现及空牌库处理，按 phase4-acceptance.md 中列出的原版规则口径执行。若更改口径，须先找原始依据并记录测试变化。

## D004 · 两层方案确认

派遣先提交暂定名单，再全员二次确认。普通行动事件／能力先进入暂定清单，确认前不执行。调整后清除对应全队二次确认，避免旧确认误用于新方案。程序按规则顺序执行，可为响应暂停。

## D005 · 信息与回退

暂定动作可撤销；已抽牌、查看牌库或揭示遭遇的信息无法收回。同机整桌撤销是纠错辅助。未来联机必须用服务器状态版本、玩家身份和确认记录，不能把当前本地 history 直接作为多人同步方案。

## D006 · 直接打开离线包

保留 index.html 加 assets 的使用方式，不要求用户安装 npm。源代码与生成页面同步提交，测试验证离线构建。实际连线图片的可用性独立验收。

## D007 · 从现有事实建立 Git 历史

现有工作目录此前没有 Git。第一次提交是 v0.9.0 快照，不伪造 v0.7.x／v0.8.x 的 Git 历史。旧版本只在发行包与 CHANGELOG 的历史记录中追溯。GitHub目标需先核对，不能把独立新历史直接强推覆盖已有远端。

## D008 · 私有仓库上传授权与历史整合

2026-10-19，用户明确同意将当前项目代码和73张基础卡图上传到私有仓库 NagisaKaworu16/lotr-lcg-web。使用独立分支 codex/project-memory-v090 与草稿PR，保留 main 及原始资料，不自动合并或公开仓库。远端导入继承原 main 历史，本地旧独立快照单独归档。

## D009 · 第五阶段按原版时序

原版规则书第16–17、31页：主动交战（每人至多1名、不受交战值限制）→玩家行动→交战检定→玩家行动。检定按起始玩家顺序循环，每次取不超过该玩家威胁的最高交战值；同值由起始玩家选择。没有普通行动插入检定循环。全队二次确认是执行前交流缓冲，不改变正式交战顺序。安都因127仅跳过检定，不跳过主动交战。强制效果优先并暂停继续执行，森林蜘蛛每次交战的加成持续整回合并叠加。

## D010 · 第六阶段确认与信息边界

敌人顺序、防御名单、玩家攻击先暂定再全队确认；响应和已揭示暗影即时处理，不塞入普通行动暂定区。暗影按玩家顺序和敌人交战值分配，同值先确定顺序；缺牌不重洗。允许在攻防步骤之间使用行动，暗影逐张取消和结算。共同防御合计防御值，但全部伤害给同一名防御者；无人防御只选己方一名英雄。角色离场即从当前及挂起攻击名单移除，重新入场不会恢复参与。插入座狼骑手用虚拟攻击者，实体仍为原暗影牌，不增加实体卡数量。第六阶段结束后停住验收。

## v0.12.0 刷新与回合结束分离

刷新的重置、威胁、先手轮换先全员确认，再按框架一次执行；蛛网选择仅暂存，不提前扣资源。普通行动在框架之后开放。阶段结束延迟效果完成后才截取回合结束触发，避免潜行攻击返回的甘道夫又被弃掉。已触发目标效果保存原目标，不因同一时点另一效果使来源脱离而撤销。新回合入口与资源收集分开，防止重复抽牌；每回合能力次数在进入下一回合后才清空。

## D011 · 智能窗口保留规则自动化（v0.13.0）

用户确认保持网页版自动化核心，不采用让玩家自行判断全部时点的TTS模式。将「空窗口让过」与「执行实际操作的确认」分开：合法性仍复用规则引擎；无可用普通行动才自动推进，或由全队明确继续当前窗口。卡牌普通行动可按本阶段忽略提醒，条件变化重新检查，新来源不继承旧实例的忽略设置。响应、强制选择、攻防和投入方案均保持独立。旧存档无设置保留详细模式，新对局默认智能；渲染不改变规则状态。


## D012 · 卡牌桌面与集中操作（v0.14.0）

用户要求结合BGA操作逻辑与诡镇网页版桌面择优改版。采用中央公共桌面、下方当前玩家、右侧流程与日志；固定操作栏说明当前任务，卡牌直接选取替代投入和攻防名单弹窗。复用原有纯前端规则引擎，不引入BGA服务器框架。界面草稿不写存档或历史；提交仍由引擎重新验证，正式效果保持全队确认。预览仅注明基础数值，特殊能力与暗影以正式结算为准。复杂目标与费用保留原选择框，避免为外观重写规则。

## D013 · R0 状态行的盒高、收缩优先级与窄屏降级（v0.15.71 修订）

三条口径由实测推翻推导后改写，**以本节为准，旧表述作废**：

1. **盒高不是 22px。** R0 的**标签行高**是 22px（`font:500 12px/22px`）；**盒高由 `.state-pill` 决定，常态 23~24px**（实测 23.55 = 11.5×1.7 + 边框 2 + padding 2）。禁止为了凑 22px 去缩 pill 的字号或内边距。验收判据为 `h ≤ 26`（抓折行导致的 >26），不是 `|h−22| ≤ 1`——后者在未改动代码的基线上就红，等于一把永远红的尺。
2. **收缩优先级：前缀可省略，数字永不省略。** 威胁值是这一行唯一随操作变化的数；前缀少两个字仍可读，数字被截成「威胁…」就失去信息。此前 `style.css` 注释与 `quest-ui.js` 注释给的是相反的结论（一份说「label 定宽、num 右侧省略」，一份说「前缀可省略、num flex:none 永不切」），**以本节为准，三处注释一并对齐**。
   **对齐锚点是左缘，不是右缘**（v0.15.72 更正，推翻了本节旧表述）：`.r0{display:flex;…;flex:0 1 auto}` 是**内容宽盒**，盒内没有多余宽度，`text-align:right` 不生效，`num.right` 恒等于 `r0.right`。fe 实测 1440 下 A→D：`num.left` 147→127、`num.right` 274→254，整列横跳 20px，成因是 pill 文案变长（约 +12）叠上 D 态 label 被 `:empty{display:none}` 抹掉（约 −32）。要右缘恒定必须让 `.r0` 撑满行，那会把数字甩到面板远端、与状态词之间拉开数百像素空白——**右缘锚定不是「另一种可选方案」，是更差的方案**。
   行为断言（缺一不可，v0.15.72 口径）：
   - **`num.left` 跨五态极差 ≤ 1**（主判据，同一 pid、同一份数据）；
   - **`pill.offsetWidth` 五态全等**（上一条成立的前提：`min-width` 抵到最宽态 C2 的固有宽，窄屏 media 内同步减 8px 水平 padding，仍须五态全等）；
   - `num.getClientRects().length === 1`（未折行）；
   - 320×568 且**内容取最宽可达值**（威胁 50、意志两位数）时 `.r0` 的 `scrollWidth ≤ 容器 clientWidth`。只测 `0 名 · 意志 0 ／ 威胁 20` 那组不足以代表最坏情况。
   **已删除的失效判据（三条，均不能在 bug 存在时变红）**：`num.scrollWidth − num.clientWidth ≤ 1`（`flex:none` 不参与收缩，逻辑恒真）；`|num.right − (r0.right − paddingRight)| ≤ 1` 与 `num.right ≤ r0.right`（内容宽盒 + 末位子项，条件恒真，实测报出 `266.36 ≤ 266.36` 这种恒等值）。
   **容器级 `r0.scrollWidth − clientWidth` 现在是有效的**：旧表述说它「不可用」是因为当时 `.r0-num` 带 `min-width:0 + overflow:hidden + ellipsis`，溢出被子元素吸收；改成 `flex:none` 之后数字不再收缩，容器会如实溢出，因此上表最后一条可用。
3. **≤600px 降级：`.r0-label` 转 sr-only，`.state-pill` 只收水平内边距。** `.r0-label` 用 `position:absolute;width:1px;height:1px;overflow:hidden;clip:rect(0 0 0 0)`——视觉消失、可访问性树保留，**几何宽度是 1 不是 0，不要用宽度判可见性**；需要判「仍在树里」时用 `textContent` + `display !== 'none'`。`.state-pill` 由 `padding:1px 8px` 收到 `1px 4px`（77.16 → 69.16），**垂直方向必须保持 1px**，否则盒高变 21.55 / 25.55，与 U18-b、V11-2 一起漂。320×568 四人局 C2 实测：`pill 69.2 + gap 6 + num 127.2 = 202.4`，视口余量 3.6（另需扣掉内侧横向 padding 约 14，见 #12）。
4. **`.r0-label` 五态恒定，不存在空态**（v0.15.72 新增）。前缀由 `statusParts` 逐态给出：A/B/C1/C2 = 「暂定」，D = 「实际」——同一件事的两个时相，两个汉字对两个汉字，宽度严格相等。因此 `.r0-label:empty{display:none}` 是死规则，已删。**不要用「D 态留空占位」凑对齐**：那是用不可见元素假冒布局，且 D 态那些数字本来就不是暂定值，给「实际」既补位又补语义。
5. **R0 的数字串不含「威胁」，威胁归标题栏**（v0.15.72 新增）。`num` 由 `${n} 名 · 意志 ${will} ／ 威胁 ${threat}` 改为 `${n} 名 · 意志 ${will}`。
   两个理由，一个语义、一个宽度：
   - **语义**：R0 讲的是「**我的**派遣」——几名、多少意志。威胁是全局局面值，不属于「谁交了什么」。挤在同一个数字串里，切人时威胁不变却跟着重绘，容易被误读成「也随派遣变化」。
   - **宽度**：威胁已有**三处**显示（`desktop-ui.js` 探查区标题「总威胁 N」常驻、`quest-ui.js:208` 面板标题「探查区威胁 N」、结算文案），R0 是第四处重复。而「五态等宽」把 pill 拉到 69.16 后，A/D 态各让出 35px 给等宽——**代价必须从别处还回去**。ux 与 visual 对齐后实测：最坏可达内容 `12 名 · 意志 34 ／ 威胁 50`（四人局每人 3 名英雄全投，20 字符）文字宽 **148.81**，超出 320 容器内容盒（286−139.16=146.84）**1.97px**——0.5 容差的 4 倍，不是字体取整波动，并冒出 2px 横向滚动条。去掉威胁后最宽值约 105px，余量约 +42（待实测）。数字明细见本节「320 的余量到底是多少」表。
   - **不准用换行解决**：R0 从 23.55 变约 47，直接破 V11-2 / U18-b，等于用「永久变高」换「偶发溢出」。
   - **威胁不能因此丢**：`quest-ui.js:208` 的 commit 步当前只渲染标题、不带威胁，需补 `探查区威胁 N`（不补「投入意志」，那个在 R0/R1 里）。

**口径**：「没有行为断言支撑的视觉约束不算约束」。凡「谁让位给谁」「谁被牺牲」这类规则，必须同时给出可测断言。**验收归口**：R0 数字的唯一判据在 V10；V11-1/-3 是容器级检查，对 R0 内部截断是盲的，不构成双保险。

**两类判据失效形态，都要防（ux 2026-10-27 反向验证后补充）**：

- **恒真型**：断言永远为真，写了等于没写。
  - **逻辑恒真**（读代码就能看出）：`num.scrollWidth − clientWidth ≤ 1`（`flex:none` 后恒等）、`|num.right − (r0.right − paddingRight)| ≤ 1`、`scrollHeight === clientHeight`、`X02 高度差 ≤ 1px`。
  - **条件恒真**（更隐蔽，读代码看不出）：`num.right ≤ r0.right` 只有在 `.r0` 被压到小于内容宽时才可能红，而只要 num 可收缩就永远压不到那一步——实测报出 `266.36 ≤ 266.36`。立判据时要问的不是「这条能不能红」，而是「**在什么条件下它才会红，那个条件在真实缺陷里成立吗**」。
  - **输入不足型**（最隐蔽，只有主动往边界推才暴露）：判据形式没问题、写的方向也对，**是喂给它的输入不够极端**。实例：visual 版的 `V10-最坏内容` 第一版取「4 名 · 意志 99 ／ 威胁 50」，能红、看着没问题——但 4 名不是可达上限，四人局每人 3 名英雄全投是 **12 名**，换成 12 名后同样的门从「余量 5.23」翻成「−1.97」。**"这条门看起来能红"不等于"它在最坏输入下会红"**，测边界必须先把输入推到可达极值，而不是随手挑一组「比较大的数」。同理 ux 的 320 常规档只测一局数值（`4 名 · 意志 9 ／ 威胁 3`）也是这个问题。

**G1 不是恒真，它是唯一承重的判据（2026-10-27 二次澄清，防止有人把它当恒真删掉）**：G1 用的是 `Range` 量**文字真实绘制宽**（`num.getBoundingClientRect().width >= textRange.getBoundingClientRect().width − 0.5`），左右两边的量彼此独立。反向验证里它**实实在在红过**：旧实现 `88.05 ≥ 127.2 FAIL`，88.05 是被压到 88 的盒宽，127.2 是文字本该有的宽度。曾被误认作 `scrollWidth > clientWidth`（那条才是恒真，且已废）。**G1 与 G3b 不是同一件事**：G3b 测容器有没有被撑破，G1 测子元素有没有把字吃掉；旧实现下 G3b 绿、G1 红。两者互补，G1 为主。

- **该红仍绿型**：反向验证才暴露。把实现打回旧版（`num` 回 `flex:1 1 auto + min-width:0 + ellipsis`）后，`num.right ≤ r0.right`、`body 无横向滚动`、`doc 无横向滚动` **三条全绿**——因为溢出被 `ellipsis` 吸收进子元素，容器一次都不溢出。**容器级指标冒充内容级指标，比恒真更危险**：恒真一测就知道，这一类要主动破坏实现才能发现。

**「`pill.offsetWidth` 五态全等」是回归护栏，不是门禁**：旧实现的 `min-width:5.6em` 本来就是定宽，这条在旧实现下也绿——它对「收窄 pill」这类改动不可见。写进报告时要标注为护栏，不要让它变成第三条恒真。

**因此：`.r0-num` 的承重判据只有 `Range` 量文字宽（G1），容器级三条只能作补证，不能单独作门禁。** 反向验证命令：`UX_BREAK='<旧版 CSS>' node scripts/_ucheck.cjs 320x568 4`（旧版下 9/17 转红）。

**已作废的数值阈值**：`num.clientWidth ≥ 128`（320 档）。该值由 pill 尚带 `min-width:5.6em` 时的「剩余空间」推出；pill 收到 69.16 后那 8px 并未变成 num 的余量——`flex:none` 下 num 按内容定宽，恒为 127.2（`clientWidth` 整数截断读 127），任何正实现都不可能 ≥128。
**不要用阈值表达「装得下」**，它由两个不同机制决定，混在一起就会得出错的结论：
- **不切字**由**结构**保证（按内容定宽 + `overflow:visible` + 无 `ellipsis`）——结构上不可能截断，与余量无关；
- **不越界**由**余量**决定——最坏可达内容下余量是 **−1.97px**，会越出容器（见下表）。
一句话：结构保证「字不会被吃掉」，不保证「放得下」。

**320 的余量到底是多少（2026-10-27 四改；前三版分别是「精确贴边」「19.64」「5.23」，都有误）**：`num.right === r0.right` 是 `.r0` shrink-to-fit（`flex:0 1 auto` + `min-width:0`，宽度 = pill+gap+num）造成的**构造恒等**，与「有没有空位」无关——它既是 G3a 恒真的根源，也是三次误读的根源。真实余量只有一种算法：`容器内容盒右缘 − 文本渲染矩形左缘 − 文本渲染矩形宽`。320 档实测：`.decide-inline` 左 33 / 右 287 / 宽 254 / padding 0，文本左缘 139.16。

| 文本内容 | 需要 | 余量 | 说明 |
|---|---|---|---|
| `4 名 · 意志 9 ／ 威胁 3`（当前实际） | 127.20 | **+19.64** | 17 字符 |
| `4 名 · 意志 99 ／ 威胁 50` | 141.61 | **+5.23** | 19 字符，曾误当最坏 |
| **`12 名 · 意志 34 ／ 威胁 50`（最坏可达）** | **148.81** | **−1.97** | 20 字符，**门禁用这行** |
| `12 名 · 意志 99 ／ 威胁 50`（位数上界） | 148.81 | −1.97 | 与上行同宽 |
| `12 名 · 意志 34`（v0.15.72 删威胁后） | ≈105 | ≈+42 待测 | — |

固定量：320×568 四人局 C2，容器内容盒右缘 **286**、`num` 左缘 **139.16** ⇒ 可用 **146.84**。

四条测量规则，缺一条就会算错：

1. **内容盒右缘必须减 border**：`rect.right − paddingRight − borderRightWidth`。`.decide-inline` 是 `rect.right 287 / border-right 1 / padding 0` ⇒ **286**。只减 padding 会虚高 1px——ux 与 visual 各错一半，就是这一处。
2. **最坏要按「位数」取，不按「数值」取**：`tabular-nums` 下 `34` 与 `99` 等宽（148.81 == 148.81），`12 名` 比 `4 名` 多一个数字位（+7.20px）。两人的 7.2px 分歧不是量法差异，是**注入文本差一位**；同一元素上 `Range.getBoundingClientRect().width` 与 `getClientRects()` 的 max right 在单行时完全相等（127.20/127.20、148.81/148.81）。
3. **必须同时断言文本单行**（`getClientRects().length === 1`）。折行后前者给整段包围盒、后者给逐行，max right 变成「最后一行的右缘」——两者分叉的方向恰好让判据变绿。
4. **只报余量不带文本内容的数字无效**。

**结论（已升级）**：最坏可达内容 `12 名 · 意志 34 ／ 威胁 50` 在 320 下**越界 1.97px**（大于 0.5 容差 4 倍，不是字体取整波动），并冒出一条 2px 横向滚动条——**这是真实可达局面下的稳健越界，不是「贴着过」**。因此「威胁移出 R0」从「值得做」升为**必做**（见本节第 5 条）。

**措辞禁令**：不许写「精确贴边 / 余量为 0」（会让人跑去收窄 pill，白折腾）；不许写「余量充足」；**不许只报一个余量数字不带文本内容**。「20.6px 不到一个汉字宽，仍属紧」是允许的写法。

**教训（本轮四次改口的总结）**：把结构恒等式当间距事实读，会**同时**得出「恒真判据」和「假的余量结论」——两者同源，而且会在不同人身上各犯一次。同一行数字有三个真值这件事还说明：**「余量」不是行的属性，是「内容 × 可用宽」的二维函数**，报一个数必然误导。

## D014 · 待决定内容一律走非模态浮动弹窗，手牌区只留牌（v0.15.73）

**决策**：`DecisionUI.html()` 输出两态——展开时 `.decide-layer`（fixed 铺满、`pointer-events:none`）+ `.decide-box`（`pointer-events:auto`）；收起后 `.decide-badge` 角标。弹窗不再渲染进手牌区（v0.15.69 的内联方案把手牌挤没了），注入点在 `<aside class="tabletop-rail">` 之前。

**为什么非模态而不是 `showModal()`**：计划阶段出牌、探险阶段投名单都依赖**桌面点击**（手牌卡、角色卡在牌桌上，不在弹窗里），模态会锁死流程；且 PlanningUI.form 已占一个 top layer `<dialog>`，双层 showModal 会互相抢焦点。

**触发与自动的判据（沿 Arkham「must 不弹、may 才弹」）**：规则书 must（强制结算、自动抽牌、提交后按序横置、无选择的投入响应）引擎算完只留日志；may/choose/up to 才进 `pending()`，五种 kind：opening（开局弃牌）/ setup（设置揭示）/ select（防御与攻击目标草稿）/ phase（等谁放弃行动、等人提交名单——引擎自己走不完的步骤；锁定期给只读状态卡）/ window（智能模式可做的事）。

**三条实现红线**：
1. `place()` 双列分支**必须设 `paddingTop`**（v0.15.73 曾漏设，弹窗从视口 0 开始盖住标题行的玩家页签）；顶部下限 = 日志轴 top，`maxHeight` 随之重算。
2. `place()` 只在 `handle('open')` 与 resize 调用不够——`render()` 尾部也要调，否则重绘后弹窗停在旧坐标。
3. Esc 收起要让路原生 `<dialog>`（`document.querySelector('dialog[open]')` 存在即跳过），不劫持 choose()/form 的确认框。

**验收脚本两处陈旧（非重构引入，v0.15.63–69 拉取后未重跑所致）**：v0.15.67 起全员确认自动执行剧本设置，`finishSetup` 按钮点不到（check-taskbar/check-contrast 改条件点击）；提交名单会弹 `choose()` 确认框，`clickQuest` 后必须点掉 `dialog[open] #ok`（check-taskbar/check-contrast 补 acceptChoose）。browser-check nav 补 `data-encounter="tie"`（交战同值敌人选择）与「暂定本次不旅行」两分支——此前 stall 报告只看 `.operation-content`，面板搬进弹窗后显示 `buttons:[]` 属探针失明，不是真没有按钮。
